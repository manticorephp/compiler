## 1. The "collector double free" was NEVER the collector

Rev 1 handed off "the collector's own double free — its three phases have never
been exercised against a real object graph". That was wrong. The collector's
arithmetic is balanced; what it does is **make objects actually die**, which is
what exposed a refcount bug that had been silent for as long as it existed.

**`get_object_vars($o)` gave back a reference it never took, once per
object-valued property, on every call.** `Parser\Dump::payload()` calls it once
per AST node.

`emitDeclaredPropsArray` walks the class layout, boxes each property slot with
`boxRawValue` and stores the result into a fresh `assoc[string,cell]`. Every
branch of that boxer that passes the slot's word THROUGH — a cell, a string, an
object, an already-cell-repr array — hands the map a BORROWED payload. The map
is element-owning: its release walks the elements and runs `__mir_cell_drop` on
each. Retain absent, release present.

Fixed in `e7f8450` by retaining the boxed payload by tag, exactly as
`array_merge`'s erased element COPY was fixed. `boxRawValueBorrows()` is read
off `boxRawValue`'s own branches so the two cannot drift; it says NO where the
box mints a fresh +1 (a nested concrete array is rebuilt), which would leak.

`(array)$o` shares the builder and had the same bug.

### The red, in seconds, with no collector at all

`tests/aot/cases/get_object_vars_prop_rc.php` — five `get_object_vars($o)` in a
loop, then read the property back. Before: the first line is EMPTY (the `Inner`
was freed under a live `$o->in`). After: byte-identical to php.

### The original crash

`MANTICORE_AUTO_GC=8` + `dump-ast tiny.php` went from exit 133 (`mfm_free`
abort under `__mir_drop_<Program>`) to **exit 0, correct output**, with
`MANTICORE_DEBUG_VERIFY=1` also clean.

## 2. Second defect, found on the way and fixed (`25bda85`)

The collector's child walker gated on `kind === KIND_OBJ && !isStruct` — a
WIDER set than the rc system owns. On a probe class with `?Box $next`,
`?Generator $gen`, `Color $c`, `?Closure $fn` the drop released `next` and
`gen`, while the walker followed `next`, `gen` AND `c`:

- a **Generator** reached `__cc_rcadd`, which writes the rc at `ptr+8` — inside
  the frame's data; a Generator's header is string-style, rc@`-8`;
- an **enum case** is a bare ORDINAL, so `inttoptr` of `Color::Blue` (1) stores
  at address 9. The `%v == 0` null guard hides exactly the FIRST case of an
  enum and never the second. This is very likely rev 1's "cc_children
  dereferenced a null class descriptor".

The walker now asks `discardReleaseFlavor`, the same question the drop body asks
through `classDropFlavor`.

## 3. How it was actually found — the method that worked

Reading emitter predicates produced three wrong answers in a row. Each of the
following was **refuted by measurement**, not by argument:

| hypothesis | what killed it |
|---|---|
| `cc_add_root` repainting a node mid-collection | `push-during-collect: 0` |
| the root buffer moving under the collection | `begin buf == end buf`, all 7 |
| a pre-existing rc bug the collector merely delays | control with buffering ON and collection NEVER triggered ran CLEAN |
| the collector's trial deletion losing a count | per-phase trace: `-1 +1`, then `-2 +2`. Balanced |

What answered it was **`MANTICORE_CC_TRACE=1`** (new, `25bda85`): every retain
and release with its RETURN ADDRESS, plus roots, decrements, restores,
whitening, frees and the buffer address per collection. The victim's whole life
in one grep, `image lookup` on the callers, and the extra release named itself.

**The decisive control is worth reusing**: build the same binary with
`MANTICORE_AUTO_GC=<huge>` — the collector is linked and buffering is live, but
no collection ever runs. Clean there and broken at `=8` means the collection is
load-bearing; broken in both means the rc bug stands alone.

## 4. Cost of an iteration

An emitter change needs **TWO generations** to test: `bin/manticore` builds the
patched source into `gN` (whose EMITTER carries the change), and `gN` builds the
binary whose RUNTIME shows it. ~70 s each on an idle machine; 5-10 min while
other sessions are building. A *user-program* probe needs only ONE generation —
prefer it (`walk.php`, `gov.php` in `/tmp/ccrepro`).

## 5f. Type interning — measured, landed, and worth less than it looks

Following §5e's lever 1. A Zend run of the whole front end
(`tools/compile_files_mir.php` over `src/`, which is how you probe the compiler
without rebuilding it) counted **3 169 269 Types against 795 distinct** — 99.97%
duplicates. `vec` 2 099 389, `assoc` 880 904, `obj` 168 886; `vec[string]` alone
776 084.

Landed in `f3d8bdc`: `vec` / `assoc` / `obj` intern, keyed off an `id` on every

two thirds behind — `join` runs at every control-flow merge and `substitute` /

**3 169 269 → 27 543 constructions.** `array[el]` 2 099 389 → 3 199,
`array[el][key]` 880 904 → 3 543, `obj` 168 886 → 393.

⚠⚠ **And the peak moved 5%.** 1146.5 → 1088.3 MB on a full self-host build,
user CPU 72.41 → 71.84 s. The prediction from the allocation count was ~250 MB
and it was wrong: those three million Types were short-lived CHURN that the pool
recycled, so few were ever resident together. **An allocation count is not a
residency measurement** — the peak is set by what is alive at once, and only the
retained fraction of the churn shows up in it.

⚠ The scalar slots' comment warned that a keyed array would put a Type through

Static keyed caches of objects are fine in this compiler.

Not done: union types (20 398 constructions) are still not interned — the key
needs the atom list.
## 5g. ⛔ SUPERSEDED BY §5i — there is no token leak

`Lexer\Token` is the biggest live class on a build — 2 751 717 allocated,
369 645 freed, **2 382 072 live** — while `Parser\Parser` (4 472) and
`Lexer\Lexer` (4 986) are freed to the last one. So the parser dies and its
tokens do not.

What it is NOT (each checked, each negative):

- not a missing annotation: `Parser::$tokens` carries `@var Token[]` and the
  constructor `@param Token[] $tokens`;
- not the shape: `new Par((new Lex())->scan(n))` with a typed property, with a
  bare ctor param, and with the real filtered-copy loop were all built as
  probes — the plain and filtered ones free 1000 of 1000;
- not over-retention: of 63 objects in a `dump-ast` run only 9 have unbalanced
  retains, so the leaked ones are never retained too much, they are never freed;
- not the drop flavor: the buffer trace shows BOTH token buffers (the lexer's
  and the parser's filtered copy) reaching **rc 0** and being released through
  `__mir_array_release_ownel_obj`, the element-walking flavor.

What it IS, from the per-object trace:

```
[RC]  rel 0x10208f6a8 rc=0
[ORC] rel obj=0x10208f6a8 rc=0x8100000000000000   ← buffered + purple, rc 0
```

The token reaches rc 0 correctly and `__mir_rc_release` REFUSES to free it
because the collector owns it, and the collection that would reclaim it never
comes: 25 roots against a 10 000 threshold.

⚠ So a `dump-ast` of a 3-line file freeing 0 of 25 tokens is NOT a small
reproduction of the build's leak — that process simply exits before its first
collection. Why the same objects survive a full build, where collections DO
run repeatedly, is still open.

**The Zend gap this exposes**: php frees at rc 0 even for a buffered object and
removes it from the root buffer (`GC_REMOVE_FROM_BUFFER` in
`zend_objects_store_del`). We defer to the next collection instead, so between
two collections every such object is retained bytes — and that is what a peak
measures. Doing it php's way needs the buffer INDEX in the object header, the
way php keeps it in `GC_INFO`: the rc word has 56 bits of count where 32 would
do, so bits 32..55 can carry a 24-bit slot index (16M roots) and the free
becomes O(1). That is a {@see MemoryAbi} change and wants its own decision.

Dead hypotheses, each with its measurement:

- **the collector's deferred free** — 1.2% of survivors;
- **lazy bodies** (the build parses with `lazyBodies: true`, and

⚠ Two traps this cost:

## 5j. ★★★ THE MIR RETENTION TERM: a property store retains at ELEMENT depth, the caller's release does not

With the census fixed (§5i) the survivors are the MIR and the AST:
`Compile\Mir\*` is **958 725 allocated, 23 603 freed — 2.5%**, `FunctionDef`
4 820 / 0, `Effects` 410 889 / 0. Emission does try to let go: it stores
`$fn->body = new Block([], Type::void())` and then unsets the table entry. The
store releases the old Block — and the release stops there.

**Repro** (`docs/status/evidence/array-prop-drop-cascade-repro.php`, 20 lines,
deterministic): a `Blk` whose `N[] $stmts` holds 50 `Pair`s of `Leaf`s, hung off
a typed `?Blk $body`. Overwrite `$body`:

```
php:    freed 149      native: freed 1
```

Only the Blk itself dies. The trace names why:

```
ret  __mir_array_retain_obj       len=50 rc=2   ← element depth: +1 per ELEMENT
rel  __mir_array_release_obj      len=50 rc=1   ← buffer only: gives elements NOTHING
rel  __mir_array_release_ownel_obj len=50 rc=0  ← gives back exactly one
```

Two refs taken per element, one given back, so every `Pair` stalls at rc 1 and
the cascade never reaches the second level. In the IR the two sites are:

- `Blk::__construct` — `$this->stmts = $s`, retains at element depth;
- `main` — releases the caller's local with the plain buffer-only flavor.

`shareCallArgs` exists for exactly this (`new Parser($toks)` is named in its
comment as THE shape) but it proves co-ownership from the callee's PARAMETER
flavor, and the parameter is a bare `array` — "co-owns nothing at element
depth". The ref was taken by the PROPERTY STORE, which that proof never looks
at.

⚠ This is the element-drop epic's minefield, where a naive symmetric fix is
recorded as reddening 5 tests. What is new here is a 20-line deterministic red
with a php oracle, which is what that epic said was missing. **Do not fix it
without keeping this repro green and the suite at 1034.**

Second, smaller, and DELIBERATE (`UnifiedArrayRuntime::emitUnsetScan`):
`unset($assoc[$key])` never drops the VALUE — repro in
`docs/status/evidence/assoc-unset-value-repro.php` gives php 199 of 200 against
native 0. The code documents why: an element READ IS A BORROW, so dropping at
unset would free a value a live local still points at. Its precondition is
spelled out there — "the value half only becomes sound once an element read
co-owns what it hands out". Emission's drain
(`unset($module->functions[$key], $fn)`) is exactly this site.

## 5l. The element SLOT never releases what it loses — and a runtime-side fix cannot work

`FunctionDef` is 4 820 allocated and 0 freed on a build, so its whole MIR body
stays with it. Emission retires the entry with
`unset($module->functions[$key], $fn)`.

Measured (`docs/status/evidence/assoc-unset-value-repro.php` and a three-way
probe), php against native:

| operation | php | native |
|---|---:|---:|
| `unset($m[$k])` | 100/100 | **0** |
| `$m[$k] = null;` then unset | 100/100 | **0** |
| `$m[$k] = new T();` (overwrite) | 100/100 | **0** |

So it is not an `unset` quirk: **an array element slot never releases what it
overwrites**, which is the property-slot bug the rc-ownership work fixed, one
level down. `emitUnsetScan` documents the value half as deliberate (an element
READ IS A BORROW), but the OVERWRITE cases are not covered by that argument and
php frees in all three.

**A runtime-side fix was tried and reverted, because it cannot work.** Dropping
the old value inside `__mir_array_set_str` / `set_int` / `unset_*` needs to know
whether the element is rc-managed, and the only runtime evidence is the array's
repr bits — which are **not stamped for a statically typed `T[]` NOR for an
erased bare `array`**. The drop was emitted into all four helpers and fired
never: 0 of 100 either way. The helpers' spare params are `hash` / `haveHash`,
so there is no channel to pass the static flavor either.

Two ways forward, both ABI-level and both wanting their own decision:

1. **Stamp element OWNERSHIP repr on obj/cell arrays**, so the shared runtime
   can drop by repr — the `ARRAY_REPR_*` half of the element-repr work the epic
   already calls "HALF DONE".
2. **Give the set/unset helpers an element-flavor parameter** and pass the
   static flavor from every call site — mechanical, broad, and it keeps the
   knowledge where the compiler already has it.

⚠ Either way the borrow objection of `emitUnsetScan` still stands for the unset
case and must be answered first (an element read must co-own), which is why (1)
or (2) alone is not enough for `unset` — but IS enough for the overwrite cases,
where php's behaviour is unambiguous.
## 5m. ★★★ AN ELEMENT READ IS A BORROW — and that is a LIVE use-after-free today

Not a precondition, not hypothetical. `docs/status/evidence/element-read-borrow-uaf-repro.php`:

```php
function take(): T {
    $m = ['a' => new T()];
    $keep = $m['a'];   // a BORROW: no reference of its own
    unset($m);         // the array dies, releasing its elements
    return $keep;      // must still be valid
}
```

```
php:    freed_before_return=0   value=alive
native: freed_before_return=1   value=          ← reads freed memory
```

A silent wrong answer, with `MANTICORE_DEBUG_VERIFY=1` clean. It is the same
contract that blocks the element-slot drop of §5l, so ONE change closes both:
the read must co-own what it hands out.

⚠⚠ **The overwrite case is NOT exempt from this, and my earlier note in §5l
saying so was wrong.** In php `$keep = $m[$k]` takes a real reference, so php
frees the old value at `$m[$k] = x` only when nobody else holds it. Here the
read is a borrow, so releasing at the store frees it under `$keep` — the same
UAF, not a different case. Comparing php's SEMANTICS hid a difference in OUR
implementation of the read.

### The change, and why it must land in one piece

Two halves, and the codebase states the rule beside `isOwnedObj` itself:

## 5d. Still open on the collector
- Reclaim stops at 33%, not 100%: refs held through ARRAY elements are never
  trial-decremented, so a cycle closed through an array is never collected, and
  `InsertMemoryOps` leaks by design.
- **Roots pushed DURING a collection are discarded but stay `buffered`**
  (`count` is reset to 0 at the end). Such an object can never be freed by
  ordinary rc and `cc_add_root` will not re-push it (it is already purple). A
  leak, not a crash — `push-during-collect` measured 0 on `dump-ast`, so it did
  not fire here. Stealing the buffer at collection entry fixes it.
- **`gc_collect_cycles()` reclaims less than php** (t4: 800 vs 1600, t6: 78 vs
  234). Expected and pre-existing: refs held through ARRAY elements are never
  trial-decremented, so a cycle closed through an array is never collected. All
  program VALUES match php on every probe.
- `__mir_array_union` (the dynamic-bag arm of `get_object_vars`) was not audited
  for the same missing retain.

## 8. Traps that cost time (rev 1's list still stands)

Everything in rev 1 §5 holds. Add:

- ⚠⚠ **A trace added to the emitter does not appear in the next binary.** The
  builder is one generation behind and emits from ITS source. Two generations,
  always — the first traced build produced an empty log and read as "the trace
  is broken".
- ⚠⚠ **The pool recycles addresses**, so "the same pointer freed twice" in a log

  a live object. That is why the crashing free took the STRING path.

  same binary — capture the trace and resolve the callers in two lldb runs.
