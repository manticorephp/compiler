# T6 / Doctrine on gen-3 — CAPPED, and what that does and does not say

`CAP_GB=12 EVERY=6 bash tools/prof/tier.sh 6`, gen-3 (`31ed18f`), idle machine
(32 GB RAM, 10 cores, zero swap in use).

```
status=capped rc=143 elapsed_s=834
peak_rss_bytes=12896714752  peak_physical_bytes=12884901888
```

## ⚠ The peak is the CAP, not a measurement

12 896 714 752 B is 12 GiB plus one tick of overshoot. Any capped run on a
12 GiB ceiling reports approximately this number no matter how much memory the
compiler actually wanted. It is NOT comparable to a finished run's peak, and it
cannot be read as "unchanged" or "improved".

The recorded ladder figure it superficially matches (12 895 862 784 B) is the
same artifact for the same reason.

## What the run DOES say — the trajectory

| RSS | reached at |
|---:|---:|
| 1 GB | 14 s |
| 2 GB | 83 s |
| 3 GB | 195 s |
| 4 GB | 317 s |
| 5 GB | 434 s |
| 6 GB | 553 s |
| 7 GB | 675 s |
| **8 GB** | **768 s** |
| 9 GB | 792 s |
| 10 GB | 801 s |
| 11 GB | 809 s |
| 12 GB | 825 s |

Linear at ~1 GB per 118 s up to 8 GB, then **8 → 12 GB in 57 seconds**.

That terminal cliff is the target the epic already named — "the LAST 84 s that
adds 4.8 GB". It is still there, and the element-drop fix was never going to
move it: that fix repays references the FRONT strands, while the cliff is a
different root in the tail. Both facts are consistent, and neither is evidence
against the other.

## ⚠ The g139 ladder is NOT a valid baseline for this

Its TSV samples at the same ~6 s interval, but the ladder ran with
`MANTICORE_POOL=0 MANTICORE_MEMORY=rc MANTICORE_PHASE_RECLAIM=1` on a different
generation. Time-to-GB also conflates speed with memory: gen-3 reaches 3 GB at
195 s against g139's 268 s, which says nothing about consumption if gen-3 is
simply further through the work. Do not quote a delta from these two runs.

## ⚠ build.log cannot attribute the cliff

The run ends on SIGTERM, so the stage timeline is lost with the buffered
output — `build.log` stops at composer autoload discovery, which is the very
first phase. Phase attribution for the cliff needs either an unbuffered stage
print or a run that finishes.

## To get a real number

1. **Raise the cap so the run FINISHES.** 32 GB RAM with no swap in use leaves
   room for `CAP_GB=20`; a completed run yields a true peak instead of a
   ceiling reading. If it still caps, the honest headline is "T6 wants > 20 GB".
2. **Then A/B gen-1 against gen-3 back to back**, same cap, same env, idle
   machine — `BIN=/tmp/mc/gens/gen1` vs the checkout's binary. Only a matched
   pair on one machine can price this fix in bytes.
